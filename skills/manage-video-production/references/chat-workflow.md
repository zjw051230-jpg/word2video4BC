# 视频生成多 Chat 工作流

## 固定 Chat 与模型

每个项目必须建立七个独立 Codex Chat，名称和合同固定：

| Chat | 模型 | 思考程度 | 职责 |
|---|---|---|---|
| `视频生成 | 任务理解与镜头规划` | `gpt-5.6-sol` | `medium` | 理解需求、拆镜头、连续性分组、用户确认与总调度 |
| `视频生成 | 背景与关键帧` | `gpt-5.6-sol` | `medium` | 背景候选、背景定稿、关键帧提示词、生图与审核 |
| `视频生成 | 视频提示词` | `gpt-5.6-terra` | `medium` | Seedance 视频提示词、引用索引和提交计划 |
| `视频生成 | 生成提交` | `gpt-5.6-terra` | `medium` | 生成预检、素材上传、提交和远端 ID 保存 |
| `视频生成 | 监控` | `gpt-5.6-terra` | `medium` | 只查询既有任务，等待整批终态 |
| `视频生成 | 拉回` | `gpt-5.6-terra` | `medium` | 整批终态复核、下载、文件校验和分类 |
| `视频生成 | 交付与复盘` | `gpt-5.5` | `medium` | 交付包、任务日志、复盘和经验更新 |

`gpt-5.5` 必须由 CC Switch 内部本地路由精确映射到 `deepseek-v4-pro`，不得影响其他模型。

自动创建、登记和派发的合同最高只能使用 `gpt-5.6-sol / medium`。`sol/high` 只能由用户手动临时开启，脚本不得自动设置。任何 Chat 发现自己仍处于 high，必须先恢复映射表中的合同模型和 `medium`，再执行交接或完成；不得让 high 状态遗留到下一项任务。

用户手动开启 high 后，当前 Chat 立即运行 `mark-manual-high --chat <名称>`。工作结束时先在界面恢复合同模型和 `medium`，再运行 `restore-contract-model --chat <名称> --actual-model <合同模型> --actual-reasoning-effort medium`。未恢复时 `prepare-handoff` 和 `complete` 都必须拒绝。

## 视频业务门禁

1. 入口 Chat 先拆分连续镜头和明确剪辑点，记录项目、task ID、镜头组和素材缺口。
2. 共享场景先由“背景与关键帧”生成两张空背景候选，用户选定背景后才继续关键帧。
3. 每个连续视频至少规划五个关键帧。关键帧只作同一视频中的时间锚点，不得因关键帧数量拆成多个视频任务。
4. 背景和关键帧必须由用户审核。未批准不得交给“视频提示词”。
5. 视频提示词和引用索引必须由用户审核。未明确授权不得交给“生成提交”。
6. 生成提交拿到全部远端 ID 后停止，不长期轮询。
7. 监控只查询，不下载、不重提。只有 `success + failed == total` 且 `total > 0` 才交给拉回。
8. 拉回必须二次复核整批终态，只下载成功版本，保留失败记录。
9. 交付与复盘是单向终止阶段，不向入口或其他 Chat 回报；完成后只归零自己的状态。

## Thread ID 与状态策略

每个项目使用 `.codex\03_codexchat对应表.json` 保存七个互不重复的真实 thread ID、模型、思考程度、提示词路径、技能、状态、租约和反馈目标。

- `0` 表示空闲，`1` 表示占用。
- 上游必须运行 `prepare-handoff` 原子占用目标并取得 `lease_id`，然后按返回的 `dispatch_contract` 发送。
- 目标忙碌时不得发送第二项任务；按返回合同设置 5 分钟单次定时器，到点只重试原交接。
- 接收者必须用同一 `lease_id` 运行 `complete`，旧租约不能清空新任务。
- 入口派发后必须停止并等待反馈，收到匹配反馈并运行 `ack-feedback` 后才能继续。
- “交付与复盘”不反馈，入口派发后无需等待。
- 七个 Chat 必须显式按合同创建和登记，禁止使用界面默认模型或默认思考程度。
- 每个 Chat 必须亲自运行 `verify-access` 完成无害写入、读回和删除探测；文字声明不能代替实际权限。

入口首次运行 `bootstrap-status`。只有 `ready=true` 才能开始业务；否则按 `chat_creation_contracts` 创建并登记所有 Chat。
